## 1. コンセプト通りに実装されているか

かなり忠実に実装されている。

- **Java 8 制約**: `pom.xml` の `maven.compiler.source/target=1.8`。`var` / `List.of` / `java.time.*` / `jakarta.*` など Java 9 以降の API・構文は全ソースで不使用（grep で確認）。`docs/java8-features.md` にて、Java 8 自体の新機能（ラムダ・Stream・Optional 等）まであえて使わず素の Java 7〜8 止まりにしている点は、レガシー現場のコードベースを模す狙いとして筋が良い判断。
- **層分離**: Servlet → Service → DAO → JDBC が明確に分離され、SQL は DAO 層に閉じている。全 DAO で `PreparedStatement` を使用しており SQL インジェクション対策済み。
- **トランザクション/排他制御**: `LoanService#loan` / `#returnLoan` で `setAutoCommit(false)` + `commit/rollback`、`VERSION` によるオプティミスティックロックが正しく実装されている。二重貸出・二重返却の防止ロジックも仕様通り。
- **認証/認可**: `AuthFilter` / `AdminFilter` による URL 直打ち対策 + 各 Servlet 側での role 二重チェック。ログイン時のセッション固定化対策（`session.invalidate()` → 再生成）も実装済み。
- **JSP**: スクリプトレット不使用（`header.jsp` は JSTL のみ）、`c:out` により XSS 対策。

仕様書（`81-備品管理システム要求仕様.md`）と実装の間に大きな乖離は見当たらない。

## 2. まだ実装できる機能

プロジェクト自身の `docs/remaining-work.md` にも自己申告があるが、妥当な残課題として以下を確認した。

- **CSRF 対策未実装**（hidden token なし）— PRG パターンのみでは不十分。エンタープライズ用途なら優先度高め。
- **パスワードが SHA-256（ソルトなし）** — 本番想定なら BCrypt 相当への移行が望ましい。ただし「Java 標準 API のみ」という縛りとのトレードオフ。
- **一覧・履歴のページング未実装** — 全件取得のため件数増加時に問題。
- **管理者のユーザー管理画面がない**（DB へ直接 seed のみ）
- 追加候補: 監査ログ（誰がいつ何を変更したか）、CSV エクスポート、返却期限超過のリマインド通知、多言語未対応 — いずれもエンタープライズ観点での次の一手になり得る。

## 3. エンタープライズ企業が使いそうなアプリという観点

妥当性は高い。Spring / JPA を使わない「Servlet + JSP + 生 JDBC」という構成そのものが、多くの企業の基幹・レガシーシステム（2000 年代後半〜2010 年代前半に構築されたシステム）の実態を再現しており、CRUD・検索・貸出返却・履歴・権限制御という業務要件も社内システムとして典型的である。

## 4. JVM / レガシーマイグレーションの出発点として

この位置づけとしては良い土台になっている。理由:

- Java 8 限定・Spring/JPA 不使用という制約が、これから移行対象になるレガシー資産の典型を模している。
- 層分離ができているため、移行時の置き換え単位（DAO → JPA、Servlet → Spring MVC 等）が明確。
- テストが 35 件整備されており、移行前後の振る舞い比較（リグレッションテスト）の土台になる。

**補足**: 移行検証の実行環境は必ずコンテナ内の Java 8 で行うべきである。ホストの Java（本レビュー実施時点でホストは Java 17 / IBM Semeru）でビルド・テストすると、コンパイラやランタイムの差異により Java 8 特有の挙動を検証できなくなるため。
